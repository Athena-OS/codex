Every technique in this cluster starts the same way: user input reaches a function that loads a file. Close that and the class disappears; harden the runtime and the cases you miss can't escalate to RCE or read the whole disk. This page gathers the fixes in order of effectiveness - the first removes the vulnerability, the rest limit the blast radius.

<Aside type="note">
For the operator, the absence of these controls is the triage signal: user input flowing straight into an include is the bug; `allow_url_include=On` opens [RFI](../rfi/) and the `data://`/`http://` [wrappers](../wrappers/); no `open_basedir` means traversal reaches the whole filesystem. The controls below are exactly what you're hoping *isn't* in place.
</Aside>

## 1. Don't pass user input to file-loading functions

The only complete fix. The page should resolve which asset to load on the back end, with no user-controlled value reaching `include`/`require`, `file_get_contents`, `fopen`, `res.render`, `<c:import>`, `Response.WriteFile`, or any other function that reads or executes a file (the [Read vs Execute](/codex/web/lfi/#read-vs-execute) table lists the common sinks). If the template to load is fixed by the route, there is nothing to traverse.

## 2. When input must choose a file, allowlist - don't filter

If a user value genuinely selects content, map it to a known file through an allowlist rather than concatenating it into a path:

```php
// The input is a KEY, never part of the path
$pages = ['home' => 'home.php', 'about' => 'about.php', 'contact' => 'contact.php'];
$page = $pages[$_GET['page']] ?? 'home.php';   // default for anything unknown
include __DIR__ . '/pages/' . $page;
```

The allowlist can be a `match`/`switch`, a DB table of id→path, or a static JSON map. The point is identical across forms: **the user input never enters the filesystem call** - only the matched, known value does.

<Aside type="caution">
Blocklist filtering (stripping `../`, rejecting keywords) is **not** this. The entire [filter-bypasses](/codex/web/lfi/filter-bypasses/) page exists because those filters fall to encoding, non-recursive-strip, approved-path prefixes, and wrappers. The recursive strip some guides suggest -

```php
while (str_contains($input, '../')) { $input = str_replace('../', '', $input); }
```

- is strictly better than a single pass but still a blocklist; prefer the allowlist above.
</Aside>

## 3. If a path is unavoidable, canonicalize then confine

Where a real path must be accepted (a download of a user file, say), reduce it to a filename or resolve it and verify it stays inside an allowed base directory - don't trust the string you were given:

```php
$base = '/var/www/files/';
$real = realpath($base . basename($_GET['file']));   // basename drops directories; realpath resolves ../, symlinks
if ($real === false || !str_starts_with($real, $base)) {
    http_response_code(404); exit;                    // outside the jail → reject
}
readfile($real);
```

Use the platform's own primitives (`basename`, `realpath`; Node `path.basename` + `path.resolve` with a prefix check; Java `Path.normalize` + `startsWith`). Hand-rolled canonicalizers miss edge cases - the classic being that `realpath`/`basename` behave differently from a shell, so a custom check can pass input that a later `system()` call expands.

## 4. Harden the runtime (limits the blast radius)

Configuration that turns "arbitrary file read" into "a much smaller problem" - the controls that decide how far [RFI](/codex/web/lfi/rfi/), wrappers, and traversal can reach:

- **Disable remote inclusion:** `allow_url_include = Off` **and** `allow_url_fopen = Off` in `php.ini`. This kills [RFI](/codex/web/lfi/rfi/) and the `data://` / `http://` [wrappers](/codex/web/lfi/wrappers/) outright - the single highest-value LFI→RCE paths.
- **Confine the filesystem:** `open_basedir = /var/www` (PHP), or run the app in a container so there is simply no `/etc/passwd`, `id_rsa`, or sibling-app source to reach. This is what blunts path traversal even when it works.
- **Drop dangerous extensions/modules:** don't load the `expect` extension (the [`expect://`](/codex/web/lfi/wrappers/) wrapper); restrict `php://filter` where the app doesn't need it.
- **Least privilege:** run the web user with no read access to secrets it doesn't need (`/etc/shadow`, other users' homes, SSH keys) and no write access to web-served directories - the latter breaks the [upload](/codex/web/lfi/file-upload-chain/) and [log-poisoning](/codex/web/lfi/log-poisoning/) RCE chains.

## 5. Defense in depth

- **WAF** (e.g. ModSecurity): catches known traversal/wrapper patterns and, even in permissive/report-only mode, is an early-warning signal. It is evadable ([filter-bypasses](/codex/web/lfi/filter-bypasses/)) - a layer, never the fix.
- **Logging and alerting:** `../`, `php://`, `data://`, and access-log/`/proc/self/environ` reads in request parameters are high-signal. Hardening's real purpose is to make a successful attack noisier and slower, buying detection time.

## Note for non-PHP stacks

Outside PHP the *execute* path is rarer, but the *read* path (path traversal → file disclosure) is identical, and the fixes are the same: allowlist the selector, or `path.resolve`/`normalize` + base-directory check. Node's `res.render()` and Java's `<c:import>` do execute/fetch, so treat those exactly like PHP `include` - no user input in the template name, and no remote URLs.

## For the report

1. **Primary:** remove user input from the file-loading call, or map it through an allowlist to a fixed file.
2. **If a path is required:** canonicalize with platform primitives and verify containment in an allowed base directory.
3. **Runtime hardening:** `allow_url_include`/`allow_url_fopen = Off`, `open_basedir` or containerization, least-privilege web user, drop `expect`.
4. **Defense in depth:** WAF in at least report-only mode; alert on traversal/wrapper indicators.

Avoid recommending a `../` filter or a WAF as the primary fix - both are bypassable, and this cluster is a catalogue of how.
